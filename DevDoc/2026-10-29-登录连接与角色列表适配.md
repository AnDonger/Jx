# 2026-10-29 登录连接与当前角色列表适配

## 现象和依据

客户端以 `Release/Client/Game.unpacked.exe` 为准，SHA256 为 `7179134950A58DF1271E36C3F1DDCD2F12C4E0C054032175166F59FAF090E200`。

第一次真实测试停在“正在连接服务器”。Bishop 的 5622 日志显示 TCP 已建立，34 字节 ACCOUNT_BEGIN 已发送，客户端没有继续提交登录请求。用户重试对应旧 Bishop PID 47908、session 7、远端端口 35490。

对照 `VsFsbServer/VsFsbServer/Structures/s2c/AsDunInfoStructHeader.h`、`Structures/c2s/AccountLoginInfoStructHeader.h`、`Tools/PinCryptCodec.cpp`，当前客户端在底层握手后还等待业务层 0x41 初始化包，body 564 字节，status 0、action 16，body 偏移 102 为 CPinCrypt 随机值。旧 Bishop 仅等待客户端先发登录请求，双方因此互相等待。

后台 GUI IDA 对项目实际客户端进行静态分析。REA MCP 本次返回 Transport closed，随后通过本机 GUI `ida.exe` 和其 IDAPython/MCP 接口完成分析，没有切换为 Ghidra 或修改客户端。分析库、脚本与输出均在 `Test/LoginConnection`。

- GUI IDA PID 48212，目标来自 Release/Client。
- `ida-login-constants.json`：0x4477E6 检查 0x100000，0x4477F1 检查 564 字节；0x4477FF 从 body+0x66 取随机值。
- `ida-rolelist-handler.json`：0x448000 处理 0x37，取 payload+10 的角色数量，按 82 字节步长读取解压后的角色记录。
- 保留实际未知字段，不套用不同 SHA256 客户端的未核对地址。

## 源码修改

全部修改现有 C/C++ Bishop 模块，没有新增服务、Gateway、资源或配置，也没有修改客户端。

- `Sources/MultiServer/Bishop/LoginDef.h`：新增当前 564 字节登录体、82 字节角色记录及角色列表头的明确线协议结构；保留原登录结构用于旧格式兼容；增加编译期长度校验。
- `GamePlayer.h/.cpp`：连接激活时发送 0x41 初始化包，每个连接单独产生并保存随机值；按实际请求长度区分当前/原登录体；当前请求用 CPinCrypt 还原 64 字节密码缓冲，规范化 MD5 后进入原 QueryAccPwd / VerifyAccount 流程。实际认证继续由原账号服务和 SQL Server JxAccount 完成。
- 当前登录响应返回 564 字节 body，回显解码后的密码缓冲和客户端协议版本；剩余时长转换为截至时间戳。当前布局不再被旧版本号常量 1 强制拒绝，旧布局仍保留原检查。
- `Intercessor.cpp`：进入登录任务前检查完整长度，截断请求关闭连接，防止按旧结构越界解释。
- 初始化、请求校验结果、账号认证结果、角色列表发送接入有效的本地网络日志。客户端 B9/BA 等尚未实现请求仍由底层完整记录。

原角色库依然返回内部 38 字节基本信息。Bishop 针对当前客户端转换为 82 字节记录，复用 Engine 的 `CODEC_LZO` 编码。SQL Server 账号库和原 Goddess 角色库结构均未改动。当前角色库能提供姓名、性别、职业及等级；头像和其余未取得字段置零，不能据此声称新角色属性和外观已完整适配。

## 两次真实客户端结果

1. 补齐初始化包后，用户确认能进入账号输入界面，说明原连接等待已解除。
2. 用户点击登录后客户端卡住。Bishop PID 80236 的 session 15 实包已通过密码校验，02:13:11 返回 status=1，并继续收到 B9/BA 请求。分析发现角色列表仍直接转发原版未压缩内部包，空列表也没有 LZO 结束标记。

第二次部署已修正角色列表，空列表 payload 应为：

`37 03000000 <identity:DWORD> 00 00 11 00 00`

其中压缩数据长度为 3，角色数量 0，`11 00 00` 为 Engine 编码器生成的 LZO 空流结束标记。不能以省略压缩数据的旧 11 字节包代替。
