### D2写入蓝怪颜色

构造派发表 `0x7B0900` 在 `0x7B0EE2` 将槽偏移840（`0xD2 * 4`）绑定到 `0x7C5930`。该函数读取包+1的实体DWORD、包+5的属性槽BYTE，调用 `0x80F9A0`。

`0x80F9A0`应用hardnpc固定／随机属性、保存蓝怪状态、拼接名称后缀，并在末尾执行：

```text
0x80FCEF  mov esi, [edi+38h]       ; hardnpc记录的偏色值
0x80FD02  call sub_6EF5C0
0x80FD07  mov eax, [eax]           ; 取哈希节点指针
0x80FD09  mov [eax+0A30Ch], esi
```

有效资源 `Resources/settings/npc/hardnpc.txt` 第9行的环狗偏色值为182。当前完整客户端仍沿原逻辑读取此值。

### DD覆盖同一个颜色字段

同一构造派发表在 `0x7B0F56` 将槽偏移884（`0xDD * 4`）绑定到 `0x7B7E20`。该函数按实体查找后执行：

```text
0x7B7E3B  movzx esi, byte ptr [esi+5] ; 包中的颜色值
0x7B7E48  call sub_6CD390             ; 返回NPC对象指针
0x7B7E4D  mov [eax+0A2FCh], esi
```

**两个偏移不是两个不同颜色字段。** 必须结合取对象指针的函数解释：

- `0x6EF5C0`返回迭代结果，其首DWORD是哈希节点地址；D2取出这个节点后写入。
- `0x6CD390`返回同一哈希节点地址加16，即NPC对象起点；其反编译返回值为`v5 + 16`，新节点也在`node + 16`构造NPC。
- 因而`node + 0xA30C == (node + 0x10) + 0xA2FC == NPC + 0xA2FC`。

D2先写182，DD随后写0，最终同一字段为0。DD处理函数没有调用撤销蓝怪的`0x80F710`，没有移除属性、恢复原名或更换怪物模板，因此可以单独恢复模型原色并保留蓝怪身份。

这是此前仅按指令偏移搜索时遗漏的关键：相同对象有“节点地址”与“NPC起点”两种寻址方式，只比较`A30C`与`A2FC`会误认为无关。

## 其他协议与边界

- 4C中普通环狗和蓝环狗均为模板7、原名环狗，D2之后才由客户端添加属性后缀。没有证据表明蓝怪需要改用另一模型模板。
- 4D当前处理函数`0x7B5640`及生命处理`0x7B19F0`更新位置、动作、生命和同步时间等；核对的处理链不承担DD这次颜色覆盖。
- F8/26的WORD实体短ID包经`0x7B9665`分支查找实体，已存在时在`0x7B97E7`写入`NPC + 0x226C = dword_1048D18`，属于更新同步时间的路径，不是写入颜色。本次不能因该包出现频繁就推断它负责恢复原色。
- F8/21读取实体与最大生命，`0x7BA67A`写`NPC + 0x1360`，不是颜色字段。
- F0通用属性处理`0x7B7E60`中存在独立颜色变更、应用蓝怪、撤销蓝怪等不同操作，不能混用“撤销蓝怪”达到只改颜色的目的。
- 本记录单腿F0共252条，操作BYTE位于游戏包+3，仅操作6有1条、操作8有251条，未出现颜色操作0或蓝怪应用／清除操作3、4。本样本的明确颜色覆盖来自DD，不是F0清除蓝怪。
- 协议名称只作交叉参考；DD实际意义另由当前客户端读包及同字段写入指令验证，不仅依赖日志解析器命名。VsFsbGameServer近源说明中的旧版函数地址不直接套用到当前EXE。
