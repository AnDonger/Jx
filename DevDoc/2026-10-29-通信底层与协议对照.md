## 已确认问题与修改

### 本地请求日志

既有 `Common/Utils.cpp` 的 `Output` 无条件返回，`Trace` 仅在 Debug 下输出，不能用于 Release 中完整保留客户端请求。

在同一个日志工具模块新增 `TraceNetworkData`，由原有 Heaven 收包链路调用。日志写入宿主 EXE 旁的 `logs/Network`，不依赖新增配置。文件名包含进程名、PID、日期和分卷编号，达到 64 MiB 后切换文件，单条记录保持完整。记录失败通过 `OutputDebugString` 提示，不把日志异常传播到业务层。

记录的阶段：

| stage | 数据 |
| --- | --- |
| handshake | 原始 34 字节服务端握手，便于还原该会话的密钥 |
| receive | 本次网络接收新增的原始字节，可能只有半个包头，也可能含多个包 |
| frame | 重组后的完整长度帧，保留解密前的字节 |
| request | 解密后交给上层的请求，移除外层两字节长度 |
| reject | 长度错误、收包异常或回调失败等底层拒绝原因 |
| disconnect | 连接关闭 |

每条记录包含本地时间（毫秒）、PID、线程 ID、服务器对象、唯一会话号、客户端槽号、远端地址、序号、协议号、阶段说明、字节数和完整十六进制数据。

`receive.sequence` 是既有 IOCP 读操作序号；`frame` 与 `request` 使用同一组从 1 开始的会话请求序号，不能混为一个计数。连接槽复用后会话号不同。`protocol` 使用十进制；原始片段及尚未解密的阶段为 -1，避免把密文字节当成协议号。

回调模式会把前一次未收完的帧保留在缓冲区；原始片段记录使用 `SetupRead` 设置的 WSABUF 起点，仅记录新增字节，避免把保留部分再次当成新接收数据。

未知协议也会完整记录并按既有流程交给上层；本批没有增加未知协议的业务实现。已解析的日志字段目前是通信层字段。账号、角色、物品等业务字段及业务拒绝结论仍须在后续适配时接入，不能把底层日志当成全部业务解析已完成。

### 长度帧校验

- 原轮询路径遇到长度 0 会等待缓冲区接近填满，长度 1/2 可能进入错误的分包流程。
- 原回调路径使用 WORD 累计已处理字节，并且未验证长度最小值。长度 0/1 可能造成减法下溢、错误解密或循环无法推进。
- 两条路径现均在收到两字节包头后立即检查：长度至少为 3，且不大于该路径实际缓冲区容量。
- 使用 `memcpy` 读取 WORD 包头，避免未对齐指针强转。
- 半包继续等待，完整包保持边界，多包依序交付；回调路径的累计长度改为 `size_t`。
- 非法长度保留拒绝日志、清空缓冲并关闭连接；回调路径的异常也纳入既有收包异常处理。

没有切换既有 KSG 模式或更改业务协议号。
