## 许可任务的原始逻辑

| 城市 | 存档任务状态 | 材料 tuple | 需求数量 | 客户端任务清单 ID |
|---|---:|---|---:|---:|
| 玉虚宫 | 13 | `3,9,0,0`，玉骨 | 5 | 3 |
| 崇城大营 | 23 | `3,11,0,0`，碎甲 | 5 | 9 |
| 蚩尤墓 | 33 | `3,8,0,0`，火羽 | 5 | 15 |

- 状态 0：菜单出现“使用仓库”；确认 `MsgBox` 后设为 1，显示来源怪物提示并调用 `TaskNote(清单ID,0)`。
- 状态 1：仅在 `HaveNormalItem(...)>=5` 时再次显示“使用仓库”。材料不足时隐藏此选项，符合没有材料的“记录四”。
- 交付：原脚本执行五次 `DelNormalItem(...)`，通知可以使用仓库，并依次 `TaskNote(3,1)`、`TaskNote(9,1)`、`TaskNote(15,1)`，将存档状态 13、23、33 一并设为 2。因此许可跨这三个城市共用，不是只解锁当前城市。
- 储物箱：任一上述状态为 2，执行 `SetFightState(0)` 与 `OpenBox(4)`；否则显示没有许可。无论是否许可，随后设置当前城市重生地并通知玩家。
- 重生调用原文分别为 `SetRevPos(2,7)`、`SetRevPos(3,13)`、`SetRevPos(4,19)`，参数是地图 ID 与复活点 ID，不能当作地图显示坐标。

材料来自 `Resources/settings/item/001/material.txt`：三者是可叠加普通材料（上限 200），不是 `EventItem`。数材料、扣材料须按物品堆叠数量处理。对照表 `settings/petsfeed.txt`、`settings/auction/auction_item_quick_search.txt` 的 tuple 也一致。

文字分别读取 `settings/stringresource.txt` 的原条目；玉虚宫接取引导在脚本中直接给出。三份任务介绍、步骤和地图链接已经存在 `settings/taskinfo.tbl` 的 `[Task_3]`、`[Task_9]`、`[Task_15]`，不需要另造任务文本资源。

## C++ 接入所需 API 与参考范围

许可主路径缺少的 API 是 `SayTask`、`MsgBox`、`TaskNote`、`HaveNormalItem`、`DelNormalItem`。原脚本没有 Include，也不包含这些函数的 Lua 定义；对有效目录与归档 PAK 优先条目（单文件不超过 200KB）的定义搜索未找到公共 Lua 实现。需要在现有 `ScriptFuns.cpp` 注册/实现。

- `SayTask(文字或字符串ID, tasks)`：过滤每个子表的 `show`，按实际显示顺序保存回调函数名。
- `MsgBox(文字或字符串ID, 确定回调, 可选取消回调)`：本轮录包是脚本 UIAction 0 / Value 3 的确认框，与普通选项菜单不同。
- `TaskNote(ID,阶段)`：接取为阶段 0，完成原脚本给阶段 1。不能未经客户端验证直接套用另一版任务显示字段的解释。
- 计数、删除材料：按本项目资源 tuple 映射真实道具，删除一个堆叠单位并同步；不要把一个堆叠当成一个材料。Lua 参数数量须在 `GetPlayerIndex` 压栈前缓存。

源码参考：`fsb2_Source_code/Client/Core/Src/ScriptFuns.cpp` 的任务与普通道具 API，以及 `PhongThan/PhongThanSource/Sources/Core/Src/PhongThanNpcDialogLua.inl` 的旧式 `show`/回调菜单兼容逻辑。新版 fsb2 的 SayTask 使用 `Size/icons/menucallback` 表布局，与本批原始脚本不同，只作结构参考。

## 差异与边界

- 原始 PAK 的三份管理员脚本没有“物品打包”选项，正式服本轮记录中有。对 PAK 优先条目（单文件不超过 300KB）的“物品打包”搜索仅命中更新公告，未找到带新菜单的管理员脚本。本次没有凭录包补造该分支。
- 原管理员还包含“六道轮回”等其他任务；会用到 `AddCredit`、`AddNormalItem`、`AddNormalItem2` 等当前尚缺 API。本记录不把这些分支标为已经实现。
- 原始脚本恢复不等于实体已经绑定脚本；管理员 NPC 放置记录、场景箱子物件的放置/脚本关联由本轮另一部分核对。
- `Resources` 受现有 `.gitignore` 规则忽略；上述文件已写入实际目录，但不会自动出现在普通 `git status` 的未跟踪清单。本次未修改忽略规则、未暂存或提交。
- 本阶段未启停服务端、未修改 C++、数据库或客户端，也没有执行真实客户端仓库流程。后续由功能实现与客户端复测记录最终结果。

## 新版 TaskNote 客户端静态证据补充

本节在后台 GUI IDA 中读取独立 `Test/WarehouseTask/TaskClient.i64`，由 `ObjectClient.i64` 复制。IDA 数据库绑定输入与当前 `Release/Client/Game.unpacked.20261030.exe` 的 SHA-256 均为 `1480dd54638b7b7dbab9bc0afb33f4a1b5dfa0fe759d16e03276163dc2010b6c`。未打开或修改生产客户端，未执行动态仓库流程。

`0x79` 分派函数为 `0x7B5B60`，调用 `loc_6FA770`；`UIAction=3` 的分支位于 `0x6FB054`。以下偏移从协议字节 79 开始，不包含录包外层 WORD 长度：

| 偏移 | 长度 | 含义及本轮证据 |
|---|---|---|
| +7 | BYTE | Operation=0 |
| +8 | BYTE | UIAction=3 |
| +9 | BYTE | OptionNum，本任务分支不读取；录包为0 |
| +10 | BYTE | Selector，直接作为单字节任务阶段；FF为移除 |
| +11 | BYTE | Feedback，录包为1；该任务分支不读取 |
| +12 | WORD | 未知字段，未赋予语义 |
| +14 | DWORD | 任务ID，即3、9、15 |
| +18 | DWORD | DataLength，客户端仅接受1至500 |
| +22 | DataLength | 任务参数内容；本轮为单字节00 |

`0x6FB06C` 读取 Selector，保存到以任务ID为键的客户端状态；`0x6FB084` 比较是否 FF。FF 分支发 UI 事件227，参数为 `(taskId, -1)`；非 FF 分支构造 `DWORD taskId + BYTE step + Content`，发同一事件。OptionNum 不是任务阶段的低字节，因此不能照抄 fsb2 的 `OptionNum=step&255; Selector=step>>8`。

UI 事件处理 `0x4BFD40 case 227`（分支 `0x4C08A1`）再次检查第三参数是否 -1：是则 `0x6387C0(taskId)`，从任务列表解绑、释放记录并刷新界面；否则 `0x637D50(taskBuffer)`，从 `settings/taskinfo.tbl` 的 `Task_%d`、`Step_%d`、`St_%d` 读取新增/更新任务。故 Selector=FF 的作用已经由静态代码确认为移除任务，而非仅依据录包猜测。

本轮录包：接取三个仓库任务为 `OptionNum=0, Selector=0, Value=3/9/15, DataLength=1, Content=00`；交材料完成后依次发送三个任务的 `Selector=FF`。原脚本调用 `TaskNote(id,0)` 接取、`TaskNote(id,1)` 完成。仅这三个原始任务的阶段1已由录包确认为结束；不能据此把所有任务的阶段1一概解释为完成。其他任务可使用1至254作为正常进度，后续仍需按原资源及录包确认。

静态证据文件位于 `Test/WarehouseTask/`：`task-client-strings.json`（79包装函数、任务字符串）、`task-client-main.json`（任务分支汇编）、`task-client-ui.json`（事件227处理）、`task-client-final.json`（输入哈希、删除函数、完整任务分支）。`Inspect-TaskClient.py` 是最后一轮 GUI IDA 导出脚本。IDA 已正常退出。

## 普通材料生成接入

仓库材料是 genre=3，但原 `KItemSet.cpp` 和存档加载的 `item_materials` 分支此前未实现。材料资源分工已修改 `KBasPropTbl.cpp/.h`、`KItemGenerator.cpp/.h`、`KItemSet.cpp`、`KItem.cpp`：接回原有 `KBPT_MedMaterial`、`KBASICPROP_MEDMATERIAL`，从当前版本 `material.txt` 读取新表列名。新格式缺少的详细类别、等级和五行为0，符合原脚本的材料tuple；保留原旧表解析，仅在新文件不存在时寻找 `medmaterialbase.txt`。没有创建替代配置。

`Gen_Material(detail,particular,level,version,item)` 复用版本库，按资源完整tuple查找，初始化非随机生成参数、无耐久和一份数量；材料对象赋值前清空基础/需求/魔法属性，避免索引复用残留。`ItemSet.Add` 的普通材料分支已接生成器，角色DB加载由主实现分工接同一生成器。

资源静态检查：001版共有515条材料，具体类别0至514无重复；火羽8、玉骨9、碎甲11均为1×1、stack上限200。编码与行尾保持GBK/LF。证据：`Test/WarehouseTask/material-source-check.json`。本分工未编译或重启服务；编译、原生功能与实际客户端验证由主实现分工记录。材料表中其他道具存在stack上限1000，而既有数量同步为BYTE、当前堆叠实现上限255；本次未扩大该协议范围，三个仓库材料不受此限制。
